# Board Design

Board is a native status engine for desktop and terminal surfaces. It replaces repeated shell polling with a small daemon, cached state, and event hooks.

## Goals

- Keep Quickshell renders cheap enough to run every second.
- Run expensive checks on independent async intervals.
- Let scripts report failures immediately without scanning status files every few seconds.
- Keep missed hooks recoverable with slow reconciliation.
- Keep configuration explicit and understandable.
- Keep `check-agents` and `agent-tmux` out of scope.

## Runtime Model

`board run` is the background daemon. It owns check scheduling and writes cache files for renderers.

`board render` is a one-shot renderer. It reads cached state and formats it for a surface such as Quickshell or tmux. It should not run network checks, Docker queries, or shell commands in the common path.

`board check` is a direct diagnostic command. It runs one configured check unless that check is disabled.

`board once` is a batch diagnostic command. It runs enabled checks once and writes their cache.

`board event` is the script hook API. External scripts call it when status changes instead of relying on frequent file polling.

## Data Flow

```text
script/job exits
  -> board event script --name backup --health critical --text "backup failed"
  -> board writes event state
  -> Quickshell calls board render every 1s
  -> board render reads cache and shows the failure

board run every 10m
  -> native script reconciliation reads status files
  -> missed or stale events are repaired
```

## Check Types

Native checks are Rust implementations. They should be the default for hot and medium-cost checks.

Command checks wrap external programs. They are acceptable for slow or hard to replace checks, but should run only from `board run` or explicit diagnostics.

Event checks aggregate pushed state from `board event`. They are the right shape for script failures, completed jobs, and other producer-owned statuses.

Reconcile checks inspect durable state on a slow interval. They are safety nets for missed events, crashed producers, manual edits, or old cache files.

## Scheduling Policy

Hot checks can refresh from render if they are purely local and cheap.

- CPU: render refresh allowed, uses cached `/proc/stat` sample delta.
- Memory: daemon interval is enough unless the UI needs faster movement.
- Temperature: daemon interval only.

Medium checks should run in the daemon.

- Docker socket
- GPG state
- Taskwarrior panels

Expensive checks should run in the daemon, at long intervals, or stay disabled.

- Weather
- HTTP/network health
- Alertmanager queries

Event checks should not poll in the hot path. They render cached event state and use reconciliation for repair.

## Configuration

Each check is configured independently.

```toml
[[check]]
name = "scripts"
kind = "native-script-events"
enabled = true
interval = "10m"
fresh_for = "15m"

[[check]]
name = "weather"
kind = "native-weather"
enabled = false
interval = "15m"
fresh_for = "30m"

[[surface]]
name = "quickshell-bar"
checks = ["scripts", "alerts", "time", "resolv", "safe", "gpg", "docker", "cpu", "mem", "temp"]
```

Disabled checks remain in config but are skipped by daemon scheduling, batch checks, metrics, and surface renders.

## Event API

Initial command shape:

```bash
board event script --name backup --health critical --text "backup failed"
board event script --name backup --health ok --clear
```

Useful fields:

- `kind`: event namespace, for example `script`.
- `name`: producer name, for example `backup`.
- `health`: `ok`, `warning`, `critical`, or `unknown`.
- `text`: display text.
- `details`: optional diagnostic text.
- `ttl`: optional expiry duration.
- `timestamp`: generated by board unless supplied.

Events should be idempotent by `(kind, name)`. A new event replaces the old event for that producer.

## Storage

Use JSON files first.

```text
~/.cache/board/checks/<check>.json
~/.cache/board/events/<kind>.json
```

JSON is inspectable, easy to delete, and avoids a database dependency. Atomic writes should use a temporary file followed by rename.

SQLite is only justified if event history, queries, or concurrent writers become hard to keep correct with JSON files.

## Script Events

`scripts` should become a native event aggregate.

Rendering rules:

- no active failures: empty text, `ok`
- one or more warnings: warning icon/count, `warning`
- one or more critical failures: critical icon/count, `critical`
- expired events: ignored or downgraded based on config

Reconciliation runs every 10 minutes by default. It reads the legacy script-status files and rebuilds the same event aggregate. This catches missed hooks without making the bar poll files constantly.

## Alerts

Alerts should be split into two concerns.

Read-only alert status:

- query Alertmanager or `amtool`
- count warning and critical alerts
- render the same icons and counts

VPN repair:

- out of default path
- never triggered by render
- require an explicit command or config such as `allow_actions = true`

## Metrics

Metrics should export both health and values.

```text
board_check_status{check="cpu"} 0
board_check_last_run_timestamp_seconds{check="cpu"} 1784717680
board_check_value{check="cpu",metric="usage_percent"} 31
```

Native checks should return structured values internally so rendering and metrics do not parse display text.

## Implementation Order

1. Add `board event script`.
2. Add JSON event storage with atomic writes.
3. Add `native-script-events` check that aggregates script events.
4. Add slow reconciliation from legacy script-status files, default `10m`.
5. Move Quickshell `scripts` from command check to native event check.
6. Add structured values to native checks for metrics.
7. Split `alerts` into read-only native status and optional action commands.
